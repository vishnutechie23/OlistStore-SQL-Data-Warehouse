# 1. PROJECT OVERVIEW

## 1.1 Business Context

Olist is a Brazilian e-commerce marketplace platform. Its public dataset contains historical marketplace data relating to orders, customers, products, sellers, payments, reviews, and geographic locations.

This project builds an analytical data warehouse using SQL Server and the Medallion Architecture.

Raw CSV data is loaded into the Bronze layer, transformed and validated in the Silver layer, and organized into a dimensional model in the Gold layer. Power BI connects to the Gold layer to provide business reporting and insights.

## 1.2 Project Objectives

- Understand and profile a multi-table relational dataset.
- Design and implement a SQL Server data warehouse.
- Load source CSV files into raw Bronze tables.
- Clean, standardize, and validate data using SQL.
- Implement Bronze, Silver, and Gold layers.
- Design a dimensional model using fact and dimension tables.
- Validate data quality and reconcile records across layers.
- Perform SQL-based data analysis.
- Build a Power BI dashboard connected to Gold tables.
- Maintain project scripts and documentation using Git and GitHub.

## 1.3 Technology Stack

| Technology | Purpose |

| Microsoft SQL Server | Data warehouse database |

Python is used for supporting data exploration and profiling. The primary data loading and transformation workflow is implemented in SQL Server.

## 1.4 Project Scope

## 2.3 Important Dataset Concepts

- `customer_id`: Identifies the customer record associated with an order.
- `customer_unique_id`: Identifies a customer across multiple customer records and is useful for repeat-purchase analysis.
- `order_id`: Central identifier connecting orders to related records.
- `order_item_id`: Identifies an item line within an order.
- `product_id`: Identifies a product.
- `seller_id`: Identifies a seller.
- `payment_sequential`: Distinguishes payment records within an order.
- ZIP code prefix: Geographic identifier that may have multiple geolocation observations.

## 2.4 Dataset Limitations

- The dataset is historical, not a live transaction feed.
- It contains anonymized Brazilian marketplace data.
- Some NULL values are valid, particularly for delivery timestamps.
- Geolocation can contain multiple observations for the same ZIP prefix.
- Orders, items, payments, and reviews have different data grains.
- Joining multiple one-to-many tables without aggregation can inflate measures.
- Monetary values represent Brazilian Real (BRL), not Indian Rupees.

# 3. DATA WAREHOUSE ARCHITECTURE

## 3.1 Architecture Overview

The project follows the Medallion Architecture:

**Source CSV Files → Bronze → Silver → Gold → Power BI**

### Bronze Layer
Stores source-aligned raw data loaded from CSV files.

### Silver Layer
Contains cleaned, typed, standardized, and validated data.

### Gold Layer
Contains business-ready dimension and fact tables designed for analytical reporting.

### Power BI
Connects to the Gold layer and presents business performance through interactive report pages.

## 3.2 Database and Schemas

**Database:** `OlistStore_DW`

**Schemas:**
- `bronze`
- `silver`
- `gold`

All three processing layers are implemented as schemas within the same SQL Server database.

# 4. BRONZE LAYER — RAW DATA INGESTION

## 4.1 Purpose

The Bronze layer provides the initial landing area for the nine source CSV files.

It preserves source records with minimal transformation so that downstream processing can use a traceable raw data layer.

## 4.2 Implementation

The Bronze implementation includes:

- Database and schema creation.
- Source-aligned table creation.
- CSV ingestion using SQL Server `BULK INSERT`.
- Data loading and row-count verification.
- Initial data quality validation.
- Relationship identification.

The review dataset is loaded directly from its original CSV file. A separate normalized TSV staging workflow is not part of the final implementation.

## 4.3 Bronze SQL Scripts

Location: `sql/bronze/`

| Script | Purpose |
|---|---|
| CreateDatabase_schemas.sql | Creates the database and schemas |
| create_bronze_tables.sql | Creates Bronze tables |
| identify_bronze_relationships.sql | Identifies logical source relationships |
| load_bronze_tables.sql | Loads CSV files using BULK INSERT |
| validate_bronze_data.sql | Performs initial data quality checks |
| verify_bronze_loads.sql | Verifies loaded records and row counts |

## 4.4 Bronze Data Quality Observations

Some source fields contain legitimate missing values.

Examples identified during validation:

- Orders with missing approval timestamps: 160.
- Orders with missing carrier timestamps: 1,783.
- Orders with missing customer delivery timestamps: 2,965.
- Products with missing category values: 610.
- Two records each with missing weight, length, height, and width values.

Missing values are not automatically replaced with zero or arbitrary defaults.

# 5. SILVER LAYER — DATA CLEANING AND TRANSFORMATION

## 5.1 Purpose

The Silver layer prepares the raw data for reliable analytical use.

It standardizes data types, handles data quality issues, and creates cleaned tables for Gold-layer modelling.

## 5.2 Transformations

The implemented Silver transformation process includes:

- Data type conversion.
- Timestamp and date handling.
- Numeric conversion for monetary and product attributes.
- Text standardization.
- Duplicate identification and handling.
- Logical date-sequence validation.
- Relationship and key validation.
- Geolocation data processing.
- Product category translation integration.

Valid NULL values are preserved where they represent meaningful source conditions.

# 6. GOLD LAYER — DIMENSIONAL MODELLING

## 6.1 Purpose

The Gold layer provides the final business-ready data model for reporting and analysis.

It uses a star-schema approach with six dimensions and four fact tables.

**Total Gold tables: 10**

## 6.2 Dimension Tables

| Dimension | Purpose | Rows |
|---|---|---:|
| dim_customers | Customer attributes and location | 99,441 |
| dim_products | Product and category information | 32,951 |
| dim_sellers | Seller attributes and location | 3,095 |
| dim_date | Calendar attributes | 1,561 |
| dim_payment_type | Payment method descriptions | 5 |
| dim_order_status | Order status descriptions | 8 |

The date dimension covers 2016-01-01 through 2020-04-09.

## 6.3 Fact Tables

| Fact table | Grain | Rows |
|---|---|---:|
| fact_orders | One row per order | 99,441 |
| fact_order_items | One row per order item | 112,650 |
| fact_payments | One row per payment record | 103,886 |
| fact_reviews | One row per review record | 99,224 |

Each fact table maintains its own business grain.

This separation prevents incorrect aggregation when orders have multiple item lines, payments, or reviews.

## 6.4 Gold SQL Scripts

Location: `sql/gold/`

| Script | Purpose |
|---|---|
| create_gold_tables.sql | Creates Gold dimensions and facts |
| load_gold_dimensions.sql | Loads dimension tables |
| load_gold_facts.sql | Loads fact tables |
| validate_gold.sql | Validates Gold data and relationships |
| gold_analysis_queries.sql | Dedicated file for independent SQL analysis |
| gold_business_queries.sql | Dedicated file for business-question queries |

The two analysis files provide separate locations for personal SQL practice and business-oriented analysis. Their query collections can be expanded as further analysis is completed.

## 6.5 Important Modelling and Metric Rules

- Item sales value is calculated from `fact_order_items.price`.
- Freight value is calculated from `fact_order_items.freight_value`.
- Recorded payment value is calculated from `fact_payments.payment_value`.
- Payment value and item sales are separate business measures.
- Order counts must use the correct order-level grain or distinct order identifiers.
- Person-level customer analysis should use `customer_unique_id`.
- Multiple fact tables should not be joined at their original grains and then aggregated without considering row multiplication.
- Delivery metrics must account for order status and missing delivery timestamps.

# 7. POWER BI REPORT

## 7.1 Data Connection

Power BI connects to the SQL Server database `OlistStore_DW` and uses the Gold dimension and fact tables.

The warehouse performs the primary data preparation. Power BI is used for semantic modelling, DAX measures, visualizations, and interactive reporting.

## 7.2 Report Pages

The completed Power BI report contains four pages.

### Page 1 — Executive Overview
Provides a high-level view of business performance through sales, order, and customer KPIs.

### Page 2 — Product & Seller Analysis
Explores product and category performance, seller contribution, and related business metrics.

### Page 3 — Order & Delivery Analysis
Examines order status, order trends, and delivery performance.

### Page 4 — Payment & Customer Review Insights
Analyzes payment behaviour, payment methods, review scores, and customer feedback.

## 7.3 Power BI Deliverable

File: `powerbi/Dashboard.pbix`

The report is maintained in the project repository.

## 7.4 Reporting Considerations

- Display monetary amounts in Brazilian Real (BRL).
- Clearly communicate historical data coverage.
- Validate dashboard totals against SQL queries.
- Use appropriate date relationships and filter behaviour.
- Avoid double counting across fact tables.
- Define KPI calculations clearly.

# 8. DATA QUALITY AND TESTING

Validation is performed at multiple stages of the warehouse.

| Layer | Main validation focus |
|---|---|
| Bronze | Source file loading, row counts, missing values, initial data checks |
| Silver | Data types, duplicate keys, date logic, and relationship checks |
| Gold | Fact grain, dimension keys, foreign keys, and aggregate reconciliation |

The project includes dedicated validation and comparison scripts for these layers.

The goal is to ensure that data is transformed consistently and that Gold measures can be reconciled against their corresponding Silver source data.

# 10. PROJECT EXECUTION GUIDE

A new user can reproduce the main warehouse workflow using the following sequence.

## Step 1 — Download the Dataset

Download the Brazilian E-Commerce Public Dataset by Olist from Kaggle.

Extract the nine CSV files into the local `dataset/` folder.

Raw CSV files are not included in the GitHub repository.

## Step 2 — Configure SQL Server

- Install or access a compatible SQL Server instance.
- Open the project scripts in SQL Server Management Studio.
- Configure source CSV file paths in the Bronze loading script.
- Ensure SQL Server has permission to access the files.

## Step 3 — Execute Bronze Scripts

Recommended order:

1. `CreateDatabase_schemas.sql`
2. `create_bronze_tables.sql`
3. `identify_bronze_relationships.sql`
4. `load_bronze_tables.sql`
5. `validate_bronze_data.sql`
6. `verify_bronze_loads.sql`

## Step 4 — Execute Silver Scripts

1. `create_silver_tables.sql`
2. `transform_silver_data.sql`
3. `compare_bronze_vs_silver.sql`

## Step 5 — Execute Gold Scripts

1. `create_gold_tables.sql`
2. `load_gold_dimensions.sql`
3. `load_gold_facts.sql`
4. `validate_gold.sql`

## Step 6 — Connect Power BI

- Open `powerbi/Dashboard.pbix`.
- Configure the SQL Server connection for the local environment.
- Confirm that the Gold tables are available.
- Refresh the report.

**Note:** Local server names, database access, file paths, and credentials may differ between machines.

# 13. IMPORTANT DESIGN DECISIONS AND LIMITATIONS

- The warehouse uses one SQL Server database with three schemas.
- Raw CSV ingestion is performed using SQL Server `BULK INSERT`.
- Python is limited to supporting data exploration and profiling.
- The Bronze layer retains source-aligned records.
- Silver transformations preserve valid NULL values and document data quality exceptions.
- The Gold layer separates orders, items, payments, and reviews into distinct fact tables.
- Customer identity analysis distinguishes `customer_id` from `customer_unique_id`.
- Item sales, freight, and payment value are treated as separate measures.
- Raw dataset files are not committed to GitHub.
- The source data is historical and should not be interpreted as current Brazilian e-commerce performance.
