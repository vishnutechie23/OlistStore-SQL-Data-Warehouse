This document defines the project scope, source dataset, data model,

It is a blueprint for implementation. It does not claim that the

the profiling phase.

================================================================================ 1.
PROJECT OVERVIEW
================================================================================

1.1 Business context

Olist is an e-commerce marketplace platform in Brazil. The public
dataset contains anonymized historical marketplace order data, together
with related information about customers, products, sellers, payments,
reviews, delivery timestamps, and geographic locations.

The project will simulate a small analytical data platform for an
e-commerce business. Data will be ingested from CSV files, retained in a
raw Bronze layer, cleaned and integrated in a Silver layer, and shaped
into business-friendly fact and dimension tables in a Gold layer. Power
BI will consume the Gold layer to present business performance.

1.2 Main objective

Build an end-to-end SQL Server data warehouse that demonstrates the
ability to:

-   Understand a multi-table relational source dataset.
-   Design schemas and raw landing tables.
-   Load and preserve source data.
-   Clean, standardize, validate, and integrate data using SQL.
-   Design a dimensional model using facts and dimensions.
-   Create reusable SQL views and stored procedures.
-   Test data quality and reconcile totals across layers.
-   Connect Power BI to curated Gold data.
-   Explain the complete data flow and business meaning of the metrics.

1.3 Intended audience

The warehouse is designed for business analysts, sales managers,
operations teams, and management users who need reliable reporting on
sales, customers, products, sellers, payments, delivery performance, and
customer satisfaction.

1.4 Project boundaries

IN SCOPE: - Nine source CSV files from the Olist dataset. - SQL Server
database and Bronze, Silver, and Gold schemas. - Initial full load and
repeatable load procedures. - Data profiling, cleaning, validation, and
transformation. - Fact and dimension modelling. - SQL business
analysis. - Power BI report connected to Gold objects. - Technical
documentation and Git version control.

OPTIONAL / FUTURE ENHANCEMENTS: - Incremental loading and change
detection. - Automated orchestration and scheduled refresh. -
Python-based ingestion automation. - Slowly Changing Dimensions (SCD
Type 2). - Advanced customer segmentation (RFM). - More detailed
geographic analysis. - Deployment to a cloud data platform.

OUT OF SCOPE FOR THE FIRST VERSION: - Live transaction processing. -
Real-time streaming. - Predictive machine learning. - Claims about
current Brazilian e-commerce market conditions. The supplied data is
historical and covers 2016-2018.

2.3 Key dataset concepts

customer_id: Identifies the customer record associated with an order. It
is not the same as a persistent person-level customer identity.

customer_unique_id: A customer identifier that can be used to identify
the same customer across multiple customer/order records. Use this field
carefully when calculating unique customers and repeat purchase
behaviour.

order_id: The central identifier connecting an order to customer, item,
payment, and review data.

order_item_id: The line number of an item within an order. An order can
contain multiple items and therefore multiple rows in the order-items
file.

product_id: Identifies a product and connects order items to product
attributes.

seller_id: Identifies the seller responsible for an item line.

payment_sequential: Distinguishes payment records belonging to the same
order.

ZIP code prefix: A geographic key shared by customer/seller records and
geolocation data. Geolocation may contain many coordinate observations
for one prefix.

2.4 Dataset limitations

-   This is historical data, not a live operational feed.
-   The time period is 2016-2018; exact minimum and maximum timestamps
    must be verified from the downloaded data.
-   The data is anonymized.
-   Some fields are legitimately NULL, such as delivery timestamps for
    orders that were not delivered.
-   The geolocation file contains many observations and may have
    repeated ZIP prefixes.
-   Review records and payment records may have different row counts
    from orders.
-   A one-to-many join can multiply rows and inflate totals if grain is
    ignored.
-   Monetary values are in Brazilian Real (BRL), not Indian Rupees.
-   City names and category values may require standardization or
    translation.

3. BUSINESS QUESTIONS AND ANALYTICAL REQUIREMENTS
================================================================================

The warehouse should make it possible to answer the following questions.

SALES: - What is total item sales value? - What is total freight
value? - How many orders and order items were recorded? - What is the
average order value? - How do sales and order volumes change month over
month? - Which months and years have the highest sales?

PRODUCT: - Which product categories generate the highest item sales? -
Which categories have the highest order-item volume? - Which products
have the highest sales value? - How do product dimensions and weight
relate to freight costs?

CUSTOMER: - How many distinct customers (customer_unique_id)
purchased? - How many customers placed more than one order? - Which
states and cities have the highest customer/order activity? - What is
the distribution of customer purchase frequency?

SELLER: - Which sellers have the highest item sales value? - Which
sellers process the most order items? - How are sellers distributed by
state? - How does seller location relate to delivery performance?

PAYMENT: - Which payment types are most frequently used? - What is the
total recorded payment value? - What is the distribution of installment
counts? - How many payment records are associated with each order?

DELIVERY / OPERATIONS: - What is the average time from purchase to
delivery? - What percentage of delivered orders arrived after the
estimated date? - Which states or sellers have longer delivery
durations? - How many orders are cancelled, unavailable, or still in
other statuses?

CUSTOMER SATISFACTION: - What is the average review score? - What share
of reviews are low scores (for example, 1 or 2)? - How do review scores
relate to late delivery? - Which product categories have lower average
review scores?

Metric definitions must be written down before dashboard development.
For example, item sales value should be defined as SUM(price) from order
items. Freight value should be defined as SUM(freight_value). Payment
value is a separate measure from the payment table and must not be added
to item sales.

4.1 High-level flow

4.2 Database and schema naming

Database: Olist_DataWarehouse

Schemas: bronze silver gold control (optional, for execution logs and
load metadata)

The database should separate technical processing layers by schema
rather than creating three unrelated databases for the first version.

4.3 Bronze layer - raw landing

Purpose: Retain source data in a form that is as close as practical to
the original CSV data. Bronze is the traceable starting point for
downstream processing.

Proposed tables: bronze.olist_customers bronze.olist_orders
bronze.olist_order_items bronze.olist_order_payments
bronze.olist_order_reviews bronze.olist_products bronze.olist_sellers
bronze.olist_geolocation bronze.product_category_translation

Implementation: - Create source-aligned tables. - Use suitable landing
data types; VARCHAR may be used for raw CSV fields where preserving
original text is important. - Load CSV files using SQL Server Import
Wizard, BULK INSERT, or a controlled Python loader. - Record source
filename and load timestamp where practical. - Preserve NULLs and source
values in the raw landing layer. - Do not silently deduplicate or
overwrite source values. - Capture load errors and row counts.

Recommended metadata: source_file load_datetime batch_id (optional)

Bronze validation: - Compare source CSV row counts with loaded table row
counts. - Confirm all expected source files were loaded. - Check column
mapping and encoding. - Record rejected rows and load errors. - Confirm
that a second load does not accidentally append duplicate data. For an
initial full load, use a controlled truncate-and-reload process or
batch-aware load design.

4.4 Silver layer - clean and standardized data

Purpose: Create reliable, typed, consistent and validated data for
analytical use.

Proposed tables: silver.customers silver.orders silver.order_items
silver.order_payments silver.order_reviews silver.products
silver.sellers silver.geolocation_by_zip (optional curated geography)
silver.product_category_translation

Transformations: - Convert timestamp strings to appropriate DATETIME2
values. - Convert prices, freight and payment values to DECIMAL. -
Convert numeric product attributes to suitable numeric types. - Trim
unwanted whitespace from text. - Standardize state codes and category
labels where justified. - Translate product categories using the
translation file. - Identify duplicate candidate keys. - Validate
allowed order statuses and payment types. - Validate review scores and
non-negative monetary values. - Check date sequence logic. - Identify
missing and orphan foreign keys. - Preserve valid NULLs rather than
replacing them indiscriminately. - Quarantine invalid records with a
reason instead of silently deleting them.

Important date checks: - Purchase timestamp should not be after approval
timestamp when approval exists, subject to source-data investigation. -
Delivery-to-customer should not be before purchase. - Actual delivery
should be compared with estimated delivery only for appropriate order
statuses and non-NULL dates. - Do not label an undelivered order as late
solely because its delivery date is NULL. Define a separate
overdue/incomplete rule if needed.

Data quality outputs: - Row counts by table. - Duplicate counts for
candidate keys. - NULL counts by important column. - Invalid date and
numeric counts. - Orphan relationship counts. - Rejected-row counts and
rejection reasons.

4.5 Gold layer - business-ready dimensional model

Purpose: Expose a stable, understandable model for reporting and
business analysis.

The Gold layer should use a star schema where practical. Dimension
tables describe business entities; fact tables record measurable
business events.

PROPOSED DIMENSIONS:

gold.dim_customers - customer_key (surrogate primary key) -
customer_unique_id - customer_city - customer_state -
customer_zip_code_prefix - Other approved descriptive attributes

Design note: The source customer_id is associated with an order-specific
customer record. Use customer_unique_id for person-level customer
analysis. Decide and document the dimension grain before implementation.

gold.dim_products - product_key (surrogate primary key) - product_id
(source business key) - product_category_name -
product_category_name_english - product weight and dimensions - Other
descriptive product attributes

gold.dim_sellers - seller_key (surrogate primary key) - seller_id
(source business key) - seller_city - seller_state -
seller_zip_code_prefix

gold.dim_date - date_key (for example, YYYYMMDD) - full_date - day,
month, month_name - quarter, year - weekday and other calendar
attributes

Potential additional dimensions: - dim_order_status - dim_payment_type -
dim_geography

PROPOSED FACT TABLES:

gold.fact_order_items Grain: one row per order item line (order_id +
order_item_id). Possible columns: - order_id (degenerate dimension /
source reference) - order_item_id - customer_key - product_key -
seller_key - purchase_date_key - shipping_limit_date_key (if useful) -
price - freight_value - item_count (normally 1 per line)

This is the principal sales and item-level analysis fact.

gold.fact_payments Grain: one row per payment record (order_id +
payment_sequential). Possible columns: - order_id - payment_sequential -
payment_type_key or payment type attribute - payment_installments -
payment_value - relevant order date key (document the chosen date
meaning)

gold.fact_reviews Grain: one row per review record (verify review_id and
order_id uniqueness). Possible columns: - review_id - order_id -
customer_key (only if relationship is valid and unambiguous) -
review_score - review creation date key - review answer timestamp -
comment fields if required for analysis

ORDER / DELIVERY FACT OR ORDER-LEVEL VIEW: A separate order-level fact
or Gold view may be created for order status, order counts,
purchase-to-delivery duration, and estimated-vs-actual delivery. Its
grain should be one row per order. This avoids repeating order-level
measures across multiple item lines.

4.6 Critical modelling and aggregation rules

-   Do not join order items directly to payments and then sum both
    measures. An order can have multiple item rows and multiple payment
    rows. Joining these raw grains can create a many-to-many
    multiplication and inflate totals.
-   Aggregate each one-to-many table to the required grain before
    joining, or keep separate fact tables.
-   Calculate item sales from order_items.price.
-   Calculate freight from order_items.freight_value.
-   Calculate recorded payment amount from order_payments.payment_value.
-   These measures represent different business concepts and should not
    be treated as interchangeable.
-   Count orders using distinct order_id where the source grain is
    item-level.
-   Count people using distinct customer_unique_id, not customer_id.
-   Document whether cancelled, unavailable, or other non-delivered
    orders are included in each KPI.
-   Define whether revenue means item price only or item price plus
    freight.
-   Use explicit date roles for purchase, approval, shipping and
    delivery dates.
-   Validate every fact table’s grain and key uniqueness before
    reporting.

5. SQL SERVER IMPLEMENTATION PLAN
================================================================================

5.1 Environment

Recommended tools: - Microsoft SQL Server 2025 (or a compatible SQL
Server edition). - SQL Server Management Studio (SSMS). - SQL scripts
stored in Git. - Optional Python for profiling or repeatable CSV
ingestion. - Power BI Desktop for reporting. - Draw.io for architecture
and data model diagrams.

5.2 Database setup

1.  Create database Olist_DataWarehouse.
2.  Create schemas bronze, silver, gold, and optionally control.
3.  Create raw Bronze tables.
4.  Load the nine CSV files.
5.  Run Bronze validation queries.
6.  Create Silver tables with suitable data types and constraints.
7.  Develop Silver transformation procedures.
8.  Run Silver data-quality checks.
9.  Design and create Gold dimensions and facts.
10. Load Gold tables in dependency order.
11. Create reporting views and indexes where useful.
12. Run end-to-end reconciliation tests.

5.3 SQL concepts to demonstrate

DDL: CREATE DATABASE, CREATE SCHEMA, CREATE TABLE, ALTER TABLE.

DML: INSERT, UPDATE, DELETE, MERGE (only where appropriate and carefully
tested).

Data transformation: CAST, CONVERT, TRY_CONVERT, COALESCE, NULLIF, CASE,
TRIM.

Analysis: JOIN, GROUP BY, HAVING, subqueries, CTEs, recursive CTEs where
justified.

Advanced SQL: ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, SUM OVER, AVG
OVER, conditional aggregation, date functions.

Warehouse engineering: Primary keys, foreign keys, surrogate keys,
indexes, views, stored procedures, transactions, error handling,
execution logging.

5.4 Stored procedure plan

Possible procedures: - bronze.usp_load_all_raw (or individual per-file
procedures) - silver.usp_load_customers - silver.usp_load_orders -
silver.usp_load_order_items - silver.usp_load_order_payments -
silver.usp_load_order_reviews - silver.usp_load_products -
silver.usp_load_sellers - gold.usp_load_dimensions -
gold.usp_load_facts - control.usp_log_load (optional)

Use TRY…CATCH, transactions where appropriate, and logging. Keep the
first implementation simple and understandable. Do not use MERGE merely
for appearance; choose a safe insert/update strategy based on the load
design.

5.5 Load execution sequence

Initial full load: 1. Load all source CSV files into Bronze. 2. Validate
Bronze row counts and file completeness. 3. Load Silver reference tables
such as products, sellers, customers, and category translations. 4. Load
Silver orders, items, payments, reviews, and geography. 5. Run Silver
quality checks. 6. Load Gold dimensions. 7. Load Gold fact tables after
dimension keys are available. 8. Run Gold reconciliation tests. 9.
Refresh Power BI.

The exact order can be adjusted based on foreign-key dependencies.

6.3 Example DAX measures (illustrative)

Item Sales := SUM ( fact_order_items[price] )

Freight Value := SUM ( fact_order_items[freight_value] )

Order Count := DISTINCTCOUNT ( fact_order_items[order_id] )

Order Item Count := COUNTROWS ( fact_order_items )

Unique Customers := DISTINCTCOUNT ( dim_customers[customer_unique_id] )

Average Order Value := DIVIDE ( [Item Sales], [Order Count] )

Important: These are illustrative starting measures. Confirm table
relationships, filter direction, fact grain, and KPI definitions before
using them. An order-level fact may be a better source for order counts
and delivery KPIs.

6.4 Dashboard design principles

-   Use a consistent layout, font hierarchy and number formatting.
-   Display currency as BRL (R$) because the source is Brazilian.
-   Clearly label historical date coverage.
-   Use slicers consistently across relevant pages.
-   Avoid overcrowding pages with too many visuals.
-   Add tooltip definitions for non-obvious KPIs.
-   Show the selected date range.
-   Validate dashboard totals against SQL queries.
-   Do not imply that historical figures describe today’s market.

7. DATA QUALITY, TESTING AND RECONCILIATION
================================================================================

Testing is a core deliverable, not an optional final step.

7.1 Bronze checks

-   All nine expected source files exist.
-   File names and column mappings are correct.
-   Source and loaded row counts match.
-   File encoding and date parsing issues are documented.
-   Load failures are captured.
-   Repeated execution does not append accidental duplicate batches.

7.2 Silver checks

-   Candidate primary keys are unique where expected.
-   Required identifiers are not NULL.
-   Numeric values can be converted safely.
-   Price, freight and payment values are checked for invalid negatives.
-   Review scores are within the source’s valid range (profile before
    enforcing).
-   Date sequences are logically checked.
-   Foreign-key relationships are checked.
-   Missing values are classified as valid, suspicious, or invalid.
-   Duplicate and rejected rows are counted and explained.

7.3 Gold checks

-   Dimension surrogate keys are unique.
-   Fact rows have valid dimension references.
-   Fact table grain is respected.
-   No unintended many-to-many join multiplication occurs.
-   Item sales reconcile with Silver order-item data.
-   Freight totals reconcile with Silver order-item data.
-   Payment totals reconcile with Silver payment data.
-   Order counts reconcile using distinct order IDs.
-   Power BI totals match SQL validation queries.

7.4 Reconciliation examples

Bronze vs source: Source CSV row count = Bronze table row count (unless
rejected rows are explicitly documented).

Silver vs Bronze: Silver count may differ when invalid records are
quarantined or when a documented deduplication rule is applied. Every
difference must be explained.

Gold vs Silver: Gold measures should reconcile to the appropriate Silver
source at the same business grain and under the same filters.

Do not expect the sum of order-item price to equal the sum of payment
value without investigating business definitions, order statuses, and
grain.

10. RISKS AND DESIGN DECISIONS TO RECORD
================================================================================

1.  SOURCE COUNT DIFFERENCES Published row counts are reference values.
    Record exact counts from the files downloaded for this
    implementation.

2.  NULL VALUES Do not replace every NULL with zero, blank text, or a
    default date. Define treatment by column and business meaning.

3.  DUPLICATES Distinguish genuine duplicate records from valid multiple
    item, payment, or review records. Never deduplicate only because
    values look similar.

4.  FACT TABLE GRAIN Document one row’s meaning for every fact table
    before writing joins.

5.  DOUBLE COUNTING Keep order items, payments, and reviews at their own
    grains or aggregate before joining. Validate totals after every
    model change.

6.  CUSTOMER IDENTITY Distinguish customer_id from customer_unique_id in
    all customer metrics.

7.  DELIVERY METRICS Define delivered, late, cancelled, unavailable, and
    undelivered statuses carefully. Handle missing delivery timestamps
    explicitly.

8.  HISTORICAL DATA Report the source period and avoid presenting the
    dataset as current.

9.  GEOGRAPHY ZIP-prefix-to-coordinate relationships may not be
    one-to-one. Profile, aggregate, or select representative coordinates
    with a documented rule.

10. LICENSE Confirm the Kaggle license and attribution obligations
    before sharing source data, extracts, or derivative datasets.
